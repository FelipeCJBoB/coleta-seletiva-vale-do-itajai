4. Como cada cartão funciona (igual para todos)

  1. Pegar o cartão. No Trello, abra o seu cartão (coluna do seu Integrante, Etapa 2), leia o checklist e marque os itens conforme avança. Avise no grupo quando começar.
  2. Atualizar e criar a branch. git checkout main · git pull · git checkout -b feat/pbXX-resumo (ex.: feat/pb08-calendario).
  3. Ler os arquivos-esqueleto. No VS Code/Android Studio abra a pasta do seu cartão. Cada arquivo já existe, só com comentários: eles dizem o que escrever, passo a passo. Leia todos antes de começar.
  4. Trabalhar na ordem da lista. A ordem dos arquivos no cartão é a ordem certa: modelos → testes da regra → regra → interface do repositório → Fake → teste do ViewModel → ViewModel → tela → teste de interface → SQL (só depois do PB06b) → repositório SQL → dados → ligar no container.
  5. Ciclo TDD em cada regra (vermelho → verde → refatorar). (1) Escreva o teste do arquivo de teste e rode: tem que FALHAR. git commit -m "test: ...". (2) Escreva o código mínimo para passar. git commit -m "feat: ...". (3) Melhore o código sem quebrar o teste. git commit -m "refactor: ...". Dê push depois de cada commit: o CI mostra vermelho e depois verde (é a nossa evidência).
  6. Rodar tudo local. .\gradlew.bat testDebugUnitTest (PowerShell) ou ./gradlew testDebugUnitTest. Para só um teste: .\gradlew.bat testDebugUnitTest --tests "*NomeDoTeste".
  7. Abrir o Pull Request. git push -u origin feat/pbXX-resumo e abra o PR no GitHub. Preencha o modelo: o que mudou, qual cartão, como conferir, checklist. Mova o cartão para a coluna 'Revisão' do Trello.
  8. Revisão e merge. O Integrante 1 revisa (até 24 h). Corrija o que pedir. Com o CI verde e a aprovação, ele faz o merge.
  9. Fechar o cartão. Depois do merge, mova o cartão para 'Concluído' no Trello e escreva 1 linha no grupo: 'PBxx mergeado'.

6. Regras de ouro

  1. Ninguém envia código direto para a main: sempre branch + Pull Request.
  2. Teste primeiro (TDD): o commit test: vem ANTES do commit feat:. É o que o professor avalia (peso 3).
  3. Cada um mexe só na sua pasta (e no seu bloco de AppContainer/AppNavegacao). Se precisar mexer em arquivo de outro, avise no grupo antes.
  4. Travou mais de 1 dia? Avise no grupo com o erro copiado. Pedir ajuda é parte do Scrum.
  5. Dados do app são de demonstração (fictícios): nunca invente número ou horário real e nunca coloque dado pessoal.
  6. Nada de nomes nos documentos do projeto: usamos Integrante 1 a 5.

  1. Pegar o cartão. No Trello, abra o seu cartão (coluna do seu Integrante, Etapa 2), leia o checklist e marque os itens conforme avança. Avise no grupo quando começar.

  5. Ciclo TDD em cada regra (vermelho → verde → refatorar). (1) Escreva o teste do arquivo de teste e rode: tem que FALHAR. git commit -m "test: ...". (2) Escreva o código mínimo para passar. git commit -m "feat: ...". (3) Melhore o código sem quebrar o teste. git commit -m "refactor: ...". Dê push depois de cada commit: o CI mostra vermelho e depois verde (é a nossa evidência).
  6. Rodar tudo local. .\gradlew.bat testDebugUnitTest (PowerShell) ou ./gradlew testDebugUnitTest. Para só um teste: .\gradlew.bat testDebugUnitTest --tests "*NomeDoTeste".
  7. Abrir o Pull Request. git push -u origin feat/pbXX-resumo e abra o PR no GitHub. Preencha o modelo: o que mudou, qual cartão, como conferir, checklist. Mova o cartão para a coluna 'Revisão' do Trello.

R1 Modelo e função pura com teste · Toda regra de negócio nasce assim.

Uma data class guarda dados. Uma função pura recebe valores e devolve um valor (sem banco, sem tela). É a parte mais fácil de testar. O teste usa kotlin.test (@Test, assertEquals).

commonMain/.../exemplo/Tarefa.kt

package br.edu.univali.coletaseletiva.exemplo

import kotlinx.datetime.DateTimeUnit
import kotlinx.datetime.DayOfWeek
import kotlinx.datetime.LocalDate
import kotlinx.datetime.TimeZone
import kotlinx.datetime.plus
import kotlinx.datetime.todayIn
import kotlin.time.Clock

data class Tarefa(val id: Long, val titulo: String, val feita: Boolean)

fun contarPendentes(tarefas: List<Tarefa>): Int = tarefas.count { !it.feita }

fun proximoDiaUtil(data: LocalDate): LocalDate {
    var d = data.plus(1, DateTimeUnit.DAY)
    while (d.dayOfWeek == DayOfWeek.SATURDAY || d.dayOfWeek == DayOfWeek.SUNDAY) {
        d = d.plus(1, DateTimeUnit.DAY)
    }
    return d
}

fun hoje(): LocalDate = Clock.System.todayIn(TimeZone.currentSystemDefault())

R3 ViewModel com StateFlow e o teste dele · Entre o repositório e a tela.

O ViewModel guarda o ESTADO da tela (data class ...Estado) num StateFlow e expõe ações (funções). A tela só observa o estado. No teste, Dispatchers.setMain(UnconfinedTestDispatcher()) faz o viewModelScope rodar na hora; não esqueça do resetMain no @AfterTest.

commonMain/.../exemplo/TarefasViewModel.kt

package br.edu.univali.coletaseletiva.exemplo

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.launch

data class TarefasEstado(
    val carregando: Boolean = true,
    val tarefas: List<Tarefa> = emptyList(),
)

class TarefasViewModel(private val repositorio: TarefaRepositorio) : ViewModel() {
    private val _estado = MutableStateFlow(TarefasEstado())
    val estado: StateFlow<TarefasEstado> = _estado.asStateFlow()

    init {
        carregar()
    }

    private fun carregar() {
        viewModelScope.launch {
            _estado.value = TarefasEstado(carregando = false, tarefas = repositorio.listar())
        }
    }

    fun adicionar(titulo: String) {
        viewModelScope.launch {
            repositorio.adicionar(titulo)
            carregar()
        }
    }
}

R7 Repositório SQL e teste com banco em memória · Depois da tabela.

O repositório SQL implementa a interface da R2. O teste cria um SQLite em memória (some quando o teste acaba), então não precisa de celular. Fica na pasta androidUnitTest (roda na JVM).

commonMain/.../exemplo/TarefaRepositorioSql.kt

package br.edu.univali.coletaseletiva.exemplo

import br.edu.univali.coletaseletiva.dados.Banco
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext

class TarefaRepositorioSql(private val banco: Banco) : TarefaRepositorio {

    override suspend fun listar(): List<Tarefa> = withContext(Dispatchers.Default) {
        banco.tarefaQueries.listarTodas { id, titulo, feita -> Tarefa(id, titulo, feita == 1L) }
            .executeAsList()
    }

    override suspend fun adicionar(titulo: String) = withContext(Dispatchers.Default) {
        banco.tarefaQueries.inserir(titulo)
        Unit
    }

    suspend fun semearSeVazio() = withContext(Dispatchers.Default) {
        if (banco.tarefaQueries.contar().executeAsOne() == 0L) {
            listOf("Separar o lixo", "Levar as pilhas ao ponto").forEach { banco.tarefaQueries.inserir(it) }
        }
    }
}

Problemas comuns
  • java -version não mostra 17: feche e reabra o terminal; confira o JDK 17 do Temurin; no Android Studio, File > Settings > Build Tools > Gradle > Gradle JDK = 17.
  • 'SDK location not found': abra o projeto pelo Android Studio uma vez (ele cria o local.properties).
  • Gradle demorando na primeira vez: normal (baixa dependências).
  • iOS: ninguém tem Mac; os testes de iOS rodam no CI.
  • Teste falhando que você acabou de escrever é o esperado no TDD (vermelho). Só é problema se continuar vermelho depois do código.
  • Conflito de merge: quase sempre é por mexer fora do seu bloco. Avise o Integrante 1 antes de resolver.

Problemas comuns
  • java -version não mostra 17: feche e reabra o terminal; confira o JDK 17 do Temurin; no Android Studio, File > Settings > Build Tools > Gradle > Gradle JDK = 17.
  • 'SDK location not found': abra o projeto pelo Android Studio uma vez (ele cria o local.properties).
  • Gradle demorando na primeira vez: normal (baixa dependências).
  • iOS: ninguém tem Mac; os testes de iOS rodam no CI.
  • Teste falhando que você acabou de escrever é o esperado no TDD (vermelho). Só é problema se continuar vermelho depois do código.
  • Conflito de merge: quase sempre é por mexer fora do seu bloco. Avise o Integrante 1 antes de resolver.
